# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

NeZamarajSe is a Rails 8 job-hunting SaaS / personal CRM for the Bosnian IT market. It scrapes job boards, uses an AI service to extract HR emails and application deadlines, resolves corporate domains for cold outreach, lets users manage applications through a Hotwire Kanban CRM board, and sends staggered automated cover-letter emails natively through the user's own Gmail account via the Gmail API. See `README.md` for the user-facing pitch and setup instructions — this file covers what that doesn't: architecture detail and gotchas relevant to making changes.

**Hard stack rule:** stick to "The Rails Way" (Hotwire + server-rendered views). Do not introduce React/Vue or other heavy frontend frameworks.

## Stack

- Rails 8.1 / Ruby 3.3.4, PostgreSQL, Active Record Encryption for OAuth tokens (`User#access_token`/`refresh_token`). `config.active_record.encryption.support_unencrypted_data = true` (`config/application.rb`) is load-bearing, not optional boilerplate: at least one real user's tokens predate `encrypts` being added to the model and are still plaintext in the DB - without this setting, `ActiveRecord::Encryption` tries to decrypt that old plaintext for dirty-checking on every save (e.g. every OAuth re-login) and raises `ActiveRecord::Encryption::Errors::Decryption`. See `test/models/user_test.rb`'s "re-authenticating a user whose tokens predate encryption" test, which reproduces this exact failure if the setting is ever removed.
- Hotwire (Turbo Drive/Streams/Frames) + Stimulus, Tailwind CSS v4 (`tailwindcss-rails`), Propshaft, Importmap (no Node/bundler JS toolchain)
- Sidekiq + `sidekiq-cron` for background jobs and scheduling (see `config/initializers/sidekiq.rb` and `config/recurring.yml` — two overlapping scheduling mechanisms exist, see below)
- Devise + OmniAuth (`omniauth-google-oauth2`) for auth; Google OAuth also supplies the Gmail-send scope
- Scraping: Ferrum (headless Chrome) + Nokogiri
- AI: `ruby-openai` gem pointed at Groq's OpenAI-compatible endpoint (`config/initializers/openai.rb`), model `openai/gpt-oss-20b` (the original `llama-3.1-8b-instant` was retired by Groq and started 404ing - see `AiJobAnalyzerService`)
- Company/domain enrichment: Clearbit Autocomplete (free, no key) → Hunter.io (keyed) for HR email guesses
- Error tracking: Honeybadger — every background job rescues, calls `Honeybadger.notify` with job-specific context, then re-raises so Sidekiq still retries. Follow this pattern in any new job.
- Deploy: Kamal (`config/deploy.yml`, `.kamal/`)

```bash

bin/brakeman --quiet --no-pager --exit-on-warn --exit-on-error   # security static analysis
bin/bundler-audit                    # gem vulnerability audit
bin/importmap audit                  # JS dependency audit
bin/ci                               # runs the full pipeline above (see config/ci.rb) — this is the canonical CI/pre-merge check
```

Sidekiq's web UI is mounted at `/sidekiq` (auth-gated, any logged-in user). Sidekiq-cron schedule is visible there too.

CI (`.github/workflows/ci.yml`) pins a specific Chrome + chromedriver version for the `system-test` job — if `bin/rails test:system` starts failing only in CI (not locally), a Chrome/driver version mismatch there is the first thing to check, not the test itself.

Database credentials/name are in `config/database.yml` (local Postgres, `ne_zamaraj_se_development` / `_test`). None of the external credentials (`groq`, `google`, `hunter`) are required to boot the app or run the test suite — each integration degrades to "unconfigured" rather than raising.

## Architecture

### Data ingestion & enrichment pipeline
1. `ScraperConfig` rows (DB-driven, not hardcoded) define per-site CSS selectors (`card_selector`, `title_selector`, `company_selector`, `link_selector`, `next_page_selector`, plus optional `location_selector`/`date_selector`) and the seed URL. `date_selector` feeds `UniversalJobScraper#extract_expiry_date`, which handles two formats: a `<time datetime="...">` element (read the attribute directly - MojPosao) or plain text with a date range (take the *last* `DD.MM.YYYY` in it, i.e. the range's end - Klix). A source's own listing data always wins over the AI's guess for `expires_at` - see point 3. `Scrapers::UniversalJobScraper` reads a config, drives Ferrum headless Chrome, paginates up to 5 pages, and `find_or_create`s `Company`/`Job` rows. `db/seeds.rb` seeds five active configs (Dzobs IT, Dzobs Management, ITBase.ba — all IT-only by nature of their sites — plus MojPosao and Klix Posao, both unfiltered general-market sources, since keyword matching at the `UserPreference` level is what actually narrows results per user) plus a Jooble config that's mapped but left commented out: `ba.jooble.org` serves headless Ferrum a Cloudflare challenge it can't get past (same wall `CompanyWallScraper` hits, see below). Posao.ba and HelloIT.ba (original roadmap targets) are dead domains; substitutes were checked and rejected as unreliable — see the comments at the bottom of `db/seeds.rb` before re-investigating either.
2. `ScrapeJobBoardsJob` is Sidekiq-cron-scheduled daily and loops over every `ScraperConfig.where(active: true)` row, calling `UniversalJobScraper` for each. **This is the only thing that makes ingestion run on a schedule** — a `ScraperConfig` row with nothing calling it does nothing. Not every source fits the CSS-selector model, though: `Scrapers::ItKarijeraScraper` reads BIT Alliance's IT Karijera board (itkarijera.ba) directly from its public JSON API instead — that site is an Angular SPA whose job cards navigate via client-side router-link clicks (no `<a href>`) and never render a company name as text, so it isn't a `ScraperConfig` row at all. It's a standalone scraper wired up the same way `CompanyWallScraper` is: its own scheduled job (`ScrapeItKarijeraJob`, daily), not looped over by `ScrapeJobBoardsJob`. When a candidate source turns out to be a JS SPA or client-rendered app, check whether it has a JSON API behind it (open the network tab / capture Ferrum's `browser.network.traffic` while the page loads) before assuming it needs Ferrum+CSS-selector scraping — an API, when there is one, is more reliable than DOM scraping.
3. New `Job` rows enqueue `AnalyzeJob` → `AiJobAnalyzerService`, which re-fetches the job's own URL with an 8s connect / 12s read timeout (a plain `URI.open` with no explicit timeout used to hang the whole queue for a full 60s - the Ruby default - on each dead/slow link; several `onecontact.com.mk` links do this), strips nav/header/footer, and persists the remaining text as `job.description` (replacing the scrape-time placeholder) *before* ever calling the AI, so that part survives even if the AI call fails. Before asking the AI for `hr_email`, it checks the (already-stripped) page itself for a `mailto:` link or a bare email in the text - stripping chrome first matters, since a job board's own sitewide "contact us" link (e.g. Klix's `posao@klix.ba`, printed in the footer of every posting) would otherwise get saved as if it were that job's HR contact. Only if nothing turns up does it ask Groq/Llama for `hr_email` + `expiration_date` as strict JSON, and even then `@job.update!` uses `@job.hr_email.presence || result["hr_email"]` / same for `expires_at` - never overwriting a value already found on the page or set by the scraper from real listing data (point 1). If the AI comes back with no email and the job's company doesn't have one resolved yet, it enqueues `FindCompanyEmailJob` as a fallback (guarded by `company.primary_email.blank?` so a company with many job postings doesn't trigger a repeat Hunter.io lookup per job) - Hunter's free tier is small (~25/month), so draining a large backlog of these in one go is a deliberate call, not something to do casually.
4. `FindCompanyEmailJob` → `EmailFinderService` resolves a company's real domain via Clearbit (stripping legal suffixes like "d.o.o." from the name first) and then queries Hunter.io's domain-search for an HR/career/recruit-style address. It's the shared enrichment path for both the AI fallback above and cold-outreach companies below.
5. `Scrapers::CompanyWallScraper` crawls business directories (companywall.ba, NACE code 62.01) to seed `Company` records (`is_cold_outreach: true`) independent of job postings, each triggering its own `FindCompanyEmailJob`. It's scheduled weekly (not daily, to stay light on a Cloudflare-protected target) via `ScrapeCompanyWallJob`.

### CRM / campaign sending engine
- `Application` is the join model between `User` and `Job`, with a status enum (`wishlist → queued → applied → interviewing/rejected/offered`) driving the Kanban board (`/crm`). Status changes broadcast live over Turbo Streams (`after_update_commit -> { broadcast_status_update }` in the model) so other open tabs/board views update without a refresh.
- Single dispatch: `ApplicationsController#dispatch_email` moves the application to `queued` (not `applied`), sets `queued_at`, and enqueues `SendApplicationJob`. Guarded by three checks, in order, each with its own flash message: the `sending_enabled` kill switch, `sendable?` (see below), then the daily send cap (`remaining_daily_sends`, based on today's `queued_at` count).
- `compose.html.erb`'s template/resume pickers live inside a `<turbo-frame id="compose_preview">` that re-renders on change (GET auto-submit via `this.form.requestSubmit()`, no custom JS) showing the resolved recipient (`Application#intended_recipient`), subject, rendered body, and attachment — or a warning when there's no known contact email. The actual dispatch form inside that frame carries `data: { turbo_frame: "_top" }` so submitting it breaks out to a normal full-page redirect instead of swapping just the frame.
- Job Market cards (`/jobs`) swap their "Save to Wishlist" button for a "Saved in CRM" badge once the current user has an `Application` for that job — check `@saved_job_ids` in `JobsController#index` before adding a second entry point for the same action.
- Bulk dispatch: `ApplicationsController#bulk_dispatch` enqueues one `SendApplicationJob` per selected application with a staggered delay (`index * 5.minutes`) specifically to avoid tripping Gmail/Google spam heuristics — do not remove this stagger. Applications are partitioned by `sendable?` first (unsendable ones are skipped, not errored), then the sendable list is truncated to `remaining_daily_sends` — a big campaign over the cap still sends as much of itself as today's allowance covers rather than being rejected wholesale. `bulk_compose.html.erb` shows the resolved recipient (or a warning) inline per target, which is the campaign's confirmation step — there's no separate "are you sure" screen.
- `SendApplicationJob` → `JobApplicationMailer` renders the `CoverLetterTemplate` (Liquid-style `{{smart_tags}}`, e.g. `{{company_name}}`) with the selected Active Storage resume PDF attached, then hands the raw MIME string to `GmailSenderService`, which sends it through the Gmail API using the user's own encrypted OAuth token (`User#access_token`/`refresh_token`, refreshed on demand) — not SMTP, so outbound mail carries no bot signature. **Only after Gmail confirms the send** does the job flip the application to `applied`, set `applied_at`, and persist `sent_recipient` (from `intended_recipient`, independently computed — not `mail.to`, which during dry-run is always the user's own inbox), `sent_subject`, `sent_body`, and `gmail_message_id` (the Gmail API response's `.id`, the hook a future reply-detection feature would poll against). A failed send leaves it at `queued` and re-raises so Sidekiq retries. Don't move the `applied` transition earlier in the flow — that race (marking it sent before it actually was) is exactly what the `queued` status exists to prevent.
- **Sending safety rails** (`config/initializers/sending_safety.rb`, all env-driven, all default to the safe setting): `dry_run_emails` (default **true**) redirects every send to the user's own inbox with a `[DRY RUN]` subject tag instead of the real recipient — this is a permanent product feature, not a temporary hack, and it's what `JobApplicationMailer#apply`/`#cold_outreach` check directly (`Rails.application.config.dry_run_emails`), not something the controller decides. `sending_enabled` (default true) is the unrelated global kill switch — off blocks every dispatch regardless of dry-run state. `daily_send_cap` (default 50) is enforced via `User#remaining_daily_sends` (shared by both `ApplicationsController` and `CompaniesController` — see below), not in the job or mailer. `JobApplicationMailer::NoRecipientError` is raised by the mailer itself if `dry_run_emails` is off and no recipient exists — but each controller's own `sendable?` checks this *before* ever enqueuing, specifically so a permanently-unsendable target doesn't sit in Sidekiq retrying forever. **Going live means flipping `DRY_RUN_EMAILS=false` — nothing else** — every other piece (preview, persistence, the recipient guard, the cap, the kill switch) is already built and tested for that moment; see ROADMAP.md Track B.

### CRM depth: timeline, follow-ups, reply detection
- `application_events` is an append-only per-`Application` log (`created_at` only, no `updated_at`) with four `event_type`s: `status_change` (auto-recorded by an `after_update_commit` callback alongside the existing Turbo Stream broadcast - `status_before_last_save`/`status` become `from_status`/`to_status`), `note` (manual, via `ApplicationsController#add_note`, requires a body), `follow_up_sent`, and `reply_detected` (both written by their respective jobs, see below). Rendered on the new `applications#show` detail page - `application_event_description` in `ApplicationsHelper` turns an event into its display text.
- `applications#show` is the only place the CRM-depth fields (`contact_person`, `salary`, `interview_date`, `rejection_reason`) and the timeline live - there was no per-application detail page before this. Its form PATCHes the existing `update` action, which now branches its redirect: back to `/crm` when `params[:application]` includes `status` (the drag-and-drop path), back to the detail page otherwise.
- **Follow-up reminders are flagging + a manual, reviewed send - not automatic.** `Application#needs_follow_up?` is true once `applied?` and `(last_followed_up_at || applied_at)` is older than `Rails.application.config.follow_up_after_days` (env `FOLLOW_UP_AFTER_DAYS`, default 7 - `config/initializers/crm_settings.rb`, same permanent env-driven pattern as `sending_safety.rb`). It drives an amber badge on the Kanban card and a banner on the detail page, both linking to `compose_follow_up`/`dispatch_follow_up` - a preview-then-send flow that mirrors the original application send (`JobApplicationMailer#follow_up`, `SendFollowUpJob`), same dry-run/kill-switch/cap guards as everywhere else. A follow-up doesn't touch `status`; it only sets `last_followed_up_at` (which also resets the follow-up clock, and counts toward `User#remaining_daily_sends`) and logs a `follow_up_sent` event. It is **not** threaded onto the original Gmail thread (no `In-Reply-To`/`References` - `#apply` doesn't capture the original send's RFC 2822 `Message-ID`), so a reply to a follow-up itself won't be caught by reply detection below, which only polls the original thread.
- **Reply detection needed a Gmail OAuth scope change** - the app previously only had `gmail.send` (write-only, can't read the mailbox). `config/initializers/devise.rb` now also requests `gmail.metadata` (headers/labels only, never message body - the minimum this feature needs), added deliberately after checking with the user since it's a real privacy/product decision, not something to decide unilaterally. `prompt: "consent"` was already set, so existing users just need to sign out and back in once to grant it - a stale token without the new scope makes `GmailSenderService#thread_has_reply?` raise, which `CheckForRepliesJob` treats as this one user's problem, not a reason to stop the batch (see below). `SendApplicationJob` now also persists `gmail_thread_id` (from the Gmail API send response, not the RFC 2822 header) alongside `gmail_message_id`.
- `CheckForRepliesJob` (sidekiq-cron, every 4 hours - `check_for_replies` in `config/initializers/sidekiq.rb`) loops every `applied` `Application` with a `gmail_thread_id` and calls `GmailSenderService#thread_has_reply?` (a `get_user_thread(format: "metadata")` call - `thread.messages.size > 1` means a reply exists, since we only ever send one message to start the thread). A reply advances `applied → interviewing` and logs a `reply_detected` event. **This is the one job in the app that deliberately does not re-raise inside its per-record rescue** - unlike every other job (see the Honeybadger convention in Stack above), one user's stale token or one bad thread shouldn't stop the rest of the batch from being checked, so it logs + `Honeybadger.notify`s per-application and keeps going.

### Companies UI & cold outreach
- `CompaniesController` (`/companies`) lists every `Company` (job-board-sourced or `CompanyWallScraper`-sourced) with filters for `has_email`, `cold` (`is_cold_outreach`), `industry_code`, and `city` — the last one queries `address ILIKE` rather than the dedicated `city` column, since no scraper actually populates `city` (only the freeform `address` string). `#show` lists the company's posted jobs and exposes a manual "Find email"/"Re-run email lookup" button that just enqueues `FindCompanyEmailJob` again.
- Cold outreach reuses `CoverLetterTemplate` + `GmailSenderService` but **not** `render_content`/`JobApplicationMailer#apply` directly — those are built around a `Job` (title/location/company). `CoverLetterTemplate#render_content_for_company(company)` only substitutes `{{company_name}}` and blanks `{{job_title}}`/`{{location}}` rather than leaving literal unsubstituted tags in a sent email — write cold-outreach templates that only lean on `{{company_name}}`. `JobApplicationMailer#cold_outreach` and `SendColdOutreachJob` mirror `#apply`/`SendApplicationJob`'s structure and safety discipline (dry-run, `NoRecipientError`, only mutate state after Gmail confirms the send).
- Unlike `Application`, a `Company` can legitimately be recontacted over time, so it only tracks the *most recent* contact — `last_contacted_at`/`last_contacted_by` (a `belongs_to :user`, nullable) — rather than a full per-send history. A real outreach log is future scope (ROADMAP.md Track D), same gap as `Application`'s own timeline.
- The daily send cap is shared: `User#remaining_daily_sends` counts today's `applications.queued_at` *and* today's `contacted_companies.last_contacted_at` against the same `daily_send_cap`, since both paths send through the same Gmail account. Don't reintroduce a per-controller cap counter — both `ApplicationsController` and `CompaniesController` call the one method on `User`.
- Dashboard's "Cold Outreach Pipeline" card (`DashboardController#show`) computes three actionable counts off `Company.where(is_cold_outreach: true)` — needs an email lookup, ready to contact (has email, never contacted), already contacted — each linking into `/companies` with the matching filter params, not just a static number.
- `Company#website` and `Job#url` are scraper-sourced strings rendered as `link_to` hrefs on the company show page — run them through `ApplicationHelper#safe_external_url` first (only allows plain `http`/`https`) rather than trusting them directly; Brakeman flags an unguarded scraped URL in an href as a (weak-confidence but real) XSS vector. `jobs/index.html.erb` has the same `job.url`-in-href pattern without this guard (Brakeman doesn't flag it there due to a different query shape) — worth revisiting if it ever does get flagged.

### Daily Radar
- `UserPreference` (1:1 with `User`) stores freeform `keywords` (comma-separated, parsed via `keyword_array`) and `receive_daily_alerts`. `Job#index` and the radar job both build the same `title ILIKE` OR-chain from `keyword_array` — if you change the matching logic, update both call sites (`JobsController#index` and `SendDailyRadarJob#perform`).
- `SendDailyRadarJob` (`app/jobs/send_daily_radar_job.rb`) runs daily (scheduled in `config/initializers/sidekiq.rb`'s `Sidekiq.configure_server` hash) and emails opted-in users a digest of jobs matching their keywords from the last 24h via `RadarMailer`.

### Scheduling has two independent mechanisms
- `config/initializers/sidekiq.rb` loads a hash into `Sidekiq::Cron::Job` at boot (`scrape_job_boards_daily`, `send_radar_emails`, `scrape_company_wall_weekly`, `scrape_it_karijera_daily`).
- `config/recurring.yml` is Solid Queue's own recurring-task config (currently only a production `clear_solid_queue_finished_jobs` cleanup).
These are separate systems (Sidekiq vs. Solid Queue) — check both when adding or debugging a scheduled task.

### Multi-tenancy
All CRM data is scoped through `current_user.applications` / `current_user.cover_letter_templates` / `current_user.resumes` in controllers — there is no soft global admin bypass. Jobs and Companies are shared/global (scraped once, visible to all users); Applications, CoverLetterTemplates, and Resumes are per-user.

## Frontend/CSS gotchas

- **The page canvas (`.page-canvas` in `app/assets/tailwind/application.css`) lives on its own full-bleed `<div>`** — a direct child of `<body>` (which has `position: relative`), not on `<body>` itself and not on `<main>`. Two separate reasons, both already hit once: putting it on `<main>` gets clipped to `main`'s `container`-capped width (1280px at the `xl` breakpoint) instead of the viewport; putting it on `<body>` triggers CSS background-propagation-to-root (since `<html>` has no background of its own), which paints outside normal document stacking and bleeds through descendant elements' own opaque backgrounds instead of being blocked by them.
- **An oklch background-color does not reliably composite as opaque in this rendering path.** Confirmed concretely: the home hero used `bg-zinc-50` (oklch) meaning to fully occlude `.page-canvas`'s dot pattern behind it, and the pattern still showed through — direct computed-style/hit-testing inspection said the element *should* have blocked it, but disabling the pattern-drawing JS and only then swapping the hero to `bg-white` (not oklch) fixed it immediately. If you add a new element that needs to actively occlude something behind it (not just tint the page), use `bg-white`/`bg-black`, not a named Tailwind palette color — those are all oklch by default. This has never bitten the rest of the app because every other "opaque card" already happens to use `bg-white`.
- When adding a decorative `position: absolute` layer (the page-canvas fade on Job Market is the current example), remember an absolutely positioned element always paints **above** non-positioned in-flow siblings regardless of DOM order — the real content below/after it in the markup needs its own `relative` (or better) to stack back on top, or it'll be visually covered by the decoration instead of the other way around.

## Known constraints from the Ferrum scraper

Both `Scrapers::UniversalJobScraper` and `Scrapers::CompanyWallScraper` wait on `browser.network.wait_for_idle` (not a blind `sleep`) after navigation, which is what makes them reliable against JS-rendered pages. `CompanyWallScraper` additionally sleeps ~3.5s first for Cloudflare's interstitial redirect timer, which fires with no network activity to wait on. Ferrum is launched with `no-sandbox`/`disable-dev-shm-usage` for headless Linux/WSL compatibility, plus `disable-blink-features: AutomationControlled` for `CompanyWallScraper` specifically — note that flag alone was not enough to get `ba.jooble.org` past its (harder) Cloudflare challenge, so don't assume it's a general fix. `UniversalJobScraper` dedupes new jobs first by exact `url`, then falls back to `company_id` + `title` — aggregator sites (e.g. Jooble, if ever enabled) link through their own redirect URL rather than the original posting, so URL-only dedup would let the same job back in under a different URL.
